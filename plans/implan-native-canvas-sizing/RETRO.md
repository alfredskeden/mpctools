# Retro

## 2026-09-06: Native-image canvas sizing mode (Prep step)

| Category | Details |
|---|---|
| **Went well** | • The plan's layering held: pure math in `lib/canvas-utils.ts` → reducer state in `hooks/use-prep-workflow.ts` → panel UI, each with its own RED/GREEN/REFACTOR cycle.<br>• The prediction that render/preview/export need no changes was correct — `lib/prep-renderer.ts` and `TransformCanvas.tsx` already take `canvasWidth`/`canvasHeight` as parameters and were never touched.<br>• Behaviour-first tests held up: assertions use `data-testid`, `aria-label`, `disabled` and callback spies, no copy or class-name assertions.<br>• Final gates green: `pnpm test` 94 files / 1259 tests, all passing; `pnpm lint:ts` clean. |
| **Problems** | • The plan's core assumption — 11:15 is the only ratio the mode needs — was dropped during execution. The shipped code carries a `canvasAspect: AspectRatio` state field derived by `reduceRatio(width, height)`, so the mode works for any ratio.<br>• Consequently none of the four named constants (`CANVAS_ASPECT_W/H`, `MIN_CANVAS_STEP`, `MAX_CANVAS_STEP`) exist. Bounds are computed per ratio by `canvasStepBounds(ratio)`, and `canvasSizeForStep` / `nearestCanvasStep` both take a ratio argument the plan did not give them.<br>• Scope grew past the plan: native W/H inputs (`canvasSizeForDimension`), a `SET_CANVAS_SIZE` branch that re-locks the ratio, and a fourth analytics event `prep_native_canvas_dimension_set`.<br>• `components/prep/instruction-steps.tsx` was not on the plan's list of touched files but needed all three new callbacks plumbed through it — the plan's file inventory was incomplete. |
| **Learnings** | • Ratio is derived, never typed by the user: any `SET_CANVAS_SIZE` (preset or input) re-derives `canvasAspect`, so the step slider afterwards follows whatever ratio the user just chose. That is what made generalising cheap enough to be worth doing mid-flight.<br>• The centre-preserving position shift was factored into one reducer helper (`resizeCanvasAroundImage`) shared by both `SET_CANVAS_SIZE` and `SET_CANVAS_SIZE_STEP`, rather than duplicated per action as the plan implied.<br>• Scale-locking controls were disabled rather than hidden, as planned; `ImageControlsPanel` reads the mode off `state` and took no new prop, `DpiOverridePanel` took a `disabled` prop. |
| **Risks** | • The whole manual browser pass (TEST_STRATEGY items 31–37) is unverified: native pixel fidelity, even border growth on slider drag, export cropping, exported PNG dimensions, drag-then-resize, default-mode regression, and Outpaint session-storage pickup were never checked in a running app.<br>• `pnpm test:coverage` was not run in this session, so the enforced 100% thresholds are unconfirmed for the new branches even though the plain test run passes.<br>• Generalising to arbitrary ratios widened the input space well past what the tests cover — extreme or near-degenerate ratios reaching `canvasStepBounds` / `nearestCanvasStep` are untested at the panel level.<br>• Overlay guides still stretch to 100% canvas width, so in `native-image` mode they do not line up with the un-scaled image. Accepted and out of scope, but it is a live visual inconsistency a user will see.<br>• `CanvasSizePanel` styles the slider thumb with arbitrary Tailwind variant selectors (`[&::-webkit-slider-thumb]:…`). The ESLint rule passes them, but it sits against the spirit of the project's no-arbitrary-values rule. |
